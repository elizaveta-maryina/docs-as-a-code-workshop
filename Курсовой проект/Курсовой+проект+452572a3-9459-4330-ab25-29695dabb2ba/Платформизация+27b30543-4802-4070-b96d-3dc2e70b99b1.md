# Стратегия платформизации

Продукт можно платформизировать как B2B SaaS-систему управления заказами и синхронизации статусов для малого e-commerce. Платформенность достигается за счёт того, что система становится центром, к которому подключаются разные внешние каналы (маркетплейсы, сайт, соцсети) через интеграции и единый API, а внутри работает единая модель статусов, правила обработки и контроль ошибок синхронизации.
Также можно добавить каталог коннекторов, публичный API/вебхуки для партнёров, типовой механизм подключения каналов и настроек маппинга статусов.

## Кому продавать

Продавать можнл компаниям, у которых:

- продажи идут через 2+ канала (маркетплейс + сайт / несколько маркетплейсов / оффлайн+онлайн);

- объём заказов от сотен до тысяч в месяц;

- есть 2–20 сотрудников, которые ведут заказы, и возникают проблемы рассинхронизации статусов, ручной сверки и ошибок.

Примеры сегментов:

- малые интернет-магазины (D2C) + маркетплейсы;

- розница с оффлайн-точкой и онлайн-каналами;

- небольшие бренды, продающие через сайт и маркетплейсы.

## Стратегия монетизации

Оптимальная стратегия для такого продукта —  это периодическая подписка/лицензия, потому что ценность непрерывна - интеграции, синхронизация, контроль ошибок работают постоянно.

Варианты тарифов:

- по количеству каналов (2 / 5 / 10);

- по числу пользователей (лицензии на кол-во целовек);

- по объёму заказов/месяц (лимит + доплата за превышение).

Также возможны дополнительные услуги:

- разовый платёж за внедрение/онбординг (настройка каналов, обучение);

- платные премиум-интеграции (сложные каналы/нестандартные статусы).

## Модель бизнеса

Базовая модель для MVP – B2B, систему продается компаниям, пользователи — сотрудники компании.

Возможное расширение платформенной модели – B2B2B через партнёров-интеграторов (агентства/фриланс-интеграторы подключают каналы и внедряют систему клиентам за комиссию).



# Функциональность, которую можно заменить публичной платформой

В  курсовом проекте можно заменить функциональность интеграции с каналами продаж: получение заказов и обновлений статусов из каналов, а также отправку статусов обратно в канал, где это возможно. Эта часть проекта во многом типовая, повторяется для каждого канала и требует обработки ошибок, повторных попыток и преобразования форматов данных.

# Рыночное решение и как его использовать

Для замены можно использовать публичную интеграционную платформу класса iPaaS, например Make (Integromat) / Albato / Zapier.

## **Варианты использования iPaaS в проекте:**

### Канал → Система (получение данных)

iPaaS настраивается на получение событий/данных из канала продаж. Далее платформа приводит данные к формату системы и вызывает API системы. Например, для создания/обновления заказа и передачи изменения статуса. Система уже внутри выполняет бизнес-логику: применяет маппинг статусов, проверяет допустимость перехода, обновляет заказ, пишет историю статусов и фиксирует результат синхронизации.

### Система → Канал (обратная синхронизация, если поддерживается)

При смене статуса в системе данные отправляются в iPaaS, после чего iPaaS вызывает API канала и обновляет статус заказа.

Как итог, iPaaS берёт на себя техническую часть интеграций (подключения, преобразование данных, ретраи/ошибки), а система остаётся “ядром” системы: единая модель заказа и статусов, правила переходов, история изменений и интерфейс для сотрудников.
