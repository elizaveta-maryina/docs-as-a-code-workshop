# Функциональные и нефункциональные требования

## **1. Функциональные требования**

### Use Case 01. Вход в систему

|Раздел|Описание|
|-|-|
|**ID**|UC-01|
|**Название**|Вход пользователя в систему|
|**Акторы**|- Пользователь системы (владелец/менеджер/работник склада/администратор)
- Сервис авторизации (Auth Service)|
|**Предусловия**|- Пользователь зарегистрирован в системе
- Пользователю назначена роль|
|**Постусловия (Успех)**|- Пользователь авторизован
- Система получила идентификатор пользователя (userID) и определила права доступа согласно роли пользователя
- Открыт главный экран (реестр заказов) в соответствии с ролью|
|**Постусловия (Неудача)**|- Пользователь не авторизован
- Отображено сообщение об ошибке|
|**Основной поток**|1. Пользователь открывает страницу входа. 
2. Пользователь вводит логин и пароль. 
3. Пользователь нажимает на кнопку "Войти". 
4. Система запрашивает данные у сервиса авторизации (Auth Service). 
5. Сервис авторизации (Auth Service) возвращает результат и идентификатор пользователя (userID).
6. Система авторизует пользователя и открывает главный экран.|
|**Альтернативный поток 1**|**Введены неверные данные** 
Точка входа: Шаг 4 
4.1 Система определяет, что логин/пароль неверны. 
4.2 Система отображает сообщение "Введен неверный логин или пароль". 4.3 Use Case завершается.|
|**Исключительный поток 1 (ошибки)**|**Auth Service недоступен** 
Точка входа: Шаг 4: 
4.1 Auth Service не отвечает.
4.2 Система отображает сообщение "Вход в систему временно недоступен. Повторите попытку позже".
4.3 Use Case завершается.|
|**Бизнес-правила**|BR-01: Права доступа определяются ролью пользователя в системе.|

### Use Case 02. Управление пользователями и ролями

|Раздел|Описание|
|-|-|
|**ID**|UC-02|
|**Название**|Создание пользователя и назначение роли|
|**Акторы**|- Владелец бизнеса
- Администратор системы
- Сервис авторизации (Auth Service)|
|**Предусловия**|- Актор авторизован 
- У актора есть права управления пользователями
- Сервис авторизации (Auth Service) доступен|
|**Постусловия (Успех)**|- Учетная запись создана в Auth Service
- Пользователь создан в системе/Роль пользователя обновлена
- Назначенная роль сохранена|
|**Постусловия (Неудача)**|- Пользователь не создан/роль не изменена
- Отображено сообщение об ошибке|
|**Основной поток**|1. Актор открывает раздел "Пользователи". 
2. Актор нажимает на кнопку "Добавить пользователя". 
3. Актор вводит данные пользователя (логин, ФИО/контакт). 
4. Актор выбирает роль пользователя (владелец/менеджер/склад/администратор). 
5. Актор нажимает на кнопку "Сохранить". 
6. Система отправляет запрос в Auth Service на создание учетной записи пользователя.
7. Auth Service возвращает результат и идентификатор пользователя.
8. Система сохраняет профиль пользователя и назначенную роль, связывая с идентификатором пользователя из Auth Service.
9. Система отображает созданного пользователя в списке пользователей.|
|**Альтернативный поток 1**|**Изменение роли существующего пользователя** 
Точка входа: Шаг 2 
2.1 Актор выбирает пользователя из списка пользователей. 
2.2 Актор изменяет роль пользователя. 
2.3 Актор нажимает на кнопку "Сохранить". 
2.4 Система сохраняет изменения.|
|**Исключительный поток 1 (ошибки)**|**Логин уже существует**
Точка входа: Шаг 7
7.1 Auth Service возвращает ошибку "Логин занят".
7.2 Система отображает сообщение "Логин уже используется" и предлагает изменить логин. 
7.3 Use Case завершается.|
|**Исключительный поток 2 (ошибки)**|**Auth Service недоступен/таймаут** 
Точка входа: Шаг 6–7 
6.1/7.1 Система не получает ответ от Auth Service. 
6.2/7.2 Система отображает сообщение "Не удалось создать пользователя. Повторите попытку позже". 
6.3/7.3 Use Case завершается.|
|**Бизнес-правила**|BR-02: Только владелец/администратор может управлять пользователями и ролями. 
BR-03: Логин пользователя должен быть уникален (проверяется Auth Service).|

### Use Case 05. Получение заказов из подключённых каналов

|Раздел|Описание|
|-|-|
|**ID**|UC-05|
|**Название**|Автоматическая загрузка новых заказов из канала продаж|
|**Акторы**|- Планировщик синхронизации (Scheduler)
- Канал продаж (внешняя система) 
- Администратор/Менеджер (только для ручного запуска — альтернативный поток)|
|**Предусловия**|- Канал подключён и имеет статус "Активен"
- Настроен интервал синхронизации (например, каждые N минут)
- Доступны параметры подключения к каналу|
|**Постусловия (Успех)**|- Для каждого заказа сохранены: канал-источник и внешний идентификатор.
- Заказы отображаются в едином списке.|
|**Постусловия (Неудача)**|- Новые заказы не загружены
- Ошибка синхронизации зафиксирована в журнале|
|**Основной поток**|1. Планировщик запускает синхронизацию по расписанию. 
2. Система отправляет запрос в канал продаж на получение новых заказов (с момента последней успешной синхронизации). 
3. Канал возвращает список новых/обновлённых заказов. 
4. Система нормализует данные заказов под внутренний формат. 
5. Система сохраняет заказы в БД, обеспечивая уникальность по связке (канал + внешний ID). 
6. Система фиксирует результат операции в журнале синхронизации (успех, количество обработанных заказов).|
|**Альтернативный поток 1**|**Ручной запуск синхронизации**
Точка входа: Шаг 1
1.1 Администратор/менеджер нажимает в системе на кнопку "Синхронизировать". 
1.2 Система запускает синхронизацию по шагам 2–6.|
|**Альтернативный поток 2**|**Частичная обработка**
Точка входа: Шаг 4–5
5.1 Для части заказов данные некорректны/неполны. 
5.2 Корректные заказы сохраняются. 
5.3 Некорректные заказы фиксируются как ошибки в журнале синхронизации с указанием причины.|
|**Исключительный поток 1 (ошибки)**|**Канал недоступен / таймаут**
Точка входа: Шаг 2–3
3.1 Система не получает корректный ответ от канала.
3.2 Система фиксирует ошибку в журнале синхронизации (канал, время, причина).
3.3 Синхронизация завершается с ошибкой.|
|**Бизнес-правила**|BR-06: Заказ идентифицируется уникально связкой (канал + внешний ID) для предотвращения дублей. 
BR-07: При ошибке синхронизации должна сохраняться информация о попытке в журнале (для контроля и повторов).|

### Use Case 06. Обновление статусов заказов из канала продаж

|Раздел|Описание|
|-|-|
|**ID**|UC-06|
|**Название**|Автоматическое получение обновлений статусов заказов из канала продаж|
|**Акторы**|- Планировщик синхронизации (Scheduler)
- Канал продаж (внешняя система)
- Администратор/Менеджер (только для ручного запуска — альтернативный поток)|
|**Предусловия**|- Канал подключён и активен
- В системе есть заказы, связанные с данным каналом (канал + внешний ID) - Настроен маппинг статусов канала и внутренних статусов системы|
|**Постусловия (Успех)**|- Для затронутых заказов обновлён внутренний статус
- Изменения статусов зафиксированы в истории заказа
- Результат операции записан в журнал синхронизации|
|**Постусловия (Неудача)**|- Статусы не обновлены (или обновлены частично)
- Ошибка/конфликт зафиксированы в журнале синхронизации|
|**Основной поток**|1. Планировщик запускает синхронизацию статусов по расписанию. 
2. Система запрашивает у канала изменения статусов заказов с момента последней успешной проверки.
3. Канал возвращает список заказов с обновлёнными статусами (внешний ID + статус канала). 
4. Система сопоставляет каждый статус канала с внутренним статусом по правилам маппинга. 
5. Система проверяет допустимость перехода статуса (матрица переходов).
6. Система обновляет статус заказа, сохраняет запись в истории статусов (кто/когда/какой статус; источник - канал). 
7. Система фиксирует результат в журнале синхронизации (успех/кол-во обновлений).|
|**Альтернативный поток 1**|**Ручной запуск обновления статусов**
Точка входа: Шаг 1
1.1 Администратор/менеджер нажимает на кнопку "Обновить статусы" в системе. 
1.2 Система выполняет шаги 2–7.|
|**Альтернативный поток 2**|**Статус не найден в маппинге**
Точка входа: Шаг 4
4.1 Система не находит соответствие статуса канала внутреннему статусу. 4.2 Система не меняет статус заказа.
4.3 Система фиксирует в журнале синхронизации ошибку "Нет маппинга для статуса". 
4.4 Статус заказа не изменяется.|
|**Исключительный поток 1 (ошибки)**|**Недопустимый переход статуса**
Точка входа: Шаг 5
5.1 Система определяет, что переход из текущего статуса в новый запрещён. 
5.2 Система не меняет статус. 
5.3 Система фиксирует конфликт в журнале синхронизации (текущий статус, новый статус, причина).|
|**Исключительный поток 2 (ошибки)**|**Канал недоступен/таймаут**
Точка входа: Шаг 2–3
3.1 Система не получает корректный ответ от канала.
3.2 Система фиксирует ошибку в журнале синхронизации.
3.3 Синхронизация завершается с ошибкой.|
|**Бизнес-правила**|BR-08: Применение статуса из канала выполняется только при наличии маппинга статусов. 
BR-09: Переход статуса должен соответствовать матрице допустимых переходов. 
BR-10: В истории статусов должен фиксироваться источник изменения (канал/пользователь).|

### Use Case 09. Изменение статуса заказа пользователем и синхронизация с каналом

|Раздел|Описание|
|-|-|
|**ID**|UC-09|
|**Название**|Изменение статуса заказа и синхронизация с каналом продаж|
|**Акторы**|- Пользователь (Менеджер/Работник склада/Администратор/Владелец)
- Канал продаж (внешняя система)|
|**Предусловия**|- Пользователь авторизован
- Пользователь имеет право изменять статус заказа
- Заказ существует и доступен пользователю
- Настроен маппинг статусов (система и канал)|
|**Постусловия (Успех)**|- Статус заказа изменён в системе
- Изменение записано в историю статусов
- Обновление статуса отправлено в канал или зафиксировано как "Не поддерживается каналом"
- Результат обмена зафиксирован в журнале синхронизации|
|**Постусловия (Неудача)**|- Статус не изменён (при недопустимом переходе)
****- ****Статус изменён в системе, но синхронизация в канал завершилась с ошибкой (ошибка зафиксирована в журнале)|
|**Основной поток**|1. Пользователь открывает карточку заказа. 
2. Пользователь выбирает новый статус из доступных.

|**Альтернативный поток 1**|**Канал не поддерживает обновление статуса**

6.2 Система фиксирует в журнале "Не поддерживается каналом".

6.3 Система фиксирует ошибку в журнале синхронизации.

|**Бизнес-правила**|BR-13: Доступ к смене статусов определяется ролью.|

В рамках MVP нефункциональные требования сформулированы для категорий, которые напрямую влияют на работоспособность ключевой ценности продукта: сбор заказов и синхронизация статусов между каналами продаж, а также ежедневную работу пользователей.

Категория "Емкость" в MVP не выделялась отдельным требованием, так как MVP ориентирован на пилотирование на ограниченном числе компаний и каналов, а ожидаемые объёмы данных на старте умеренные. В данном случае риск состоит в том, что при росте заказов могут ухудшиться время отклика реестра и скорость синхронизации.
В V2/V3 планируется добавить измеримые требования по объёмам (максимальное число заказов и записей истории статусов), а также требования к производительности синхронизации при росте данных.

Категория "Масштабируемость" в MVP не выделялась отдельным требованием, так как MVP проверяет базовую ценность на ограниченном числе каналов и пользователей, и не предполагает высоких нагрузок или горизонтального масштабирования.
При подключении новых каналов и росте числа пользователей возможны деградации скорости синхронизации и усложнение сопровождения.
Начиная с V2 планируется добавить требования к масштабированию по каналам и пользователям, а также определить метрики для контроля деградации.

Таким образом, непокрытые категории не критичны для MVP, но несут управляемые риски и будут учтены в следующих версиях продукта по мере масштабирования.
